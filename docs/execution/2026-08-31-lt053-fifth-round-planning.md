## 1. 为什么第五轮的主题是「学习是否真的发生」

前四轮各有明确主题：第一轮建广度（65 个实验），第二轮补深度与专用化，第三轮扩结构性缺口，第四轮修验证体系与工程治理。

四轮之后平台有 78 个实验、14 个分类、156 个变体、48 个专用实现，`pnpm verify` 全绿，全新环境可重建，八道门禁强制一致性。**但这些证明的是「平台工程上是正确的」，不是「学习者真的学到了东西」。**

这是本项目的根本张力。`AGENTS.md` 第 1 节把定位写为「个人学习优先」，而四轮建设的重心全在内容数量与工程正确性上。学习效果从未被验证过——也从未被定义为可验证的东西。

第五轮的主题因此是：**把学习深度从「声称」变成「可机械判定」**。

## 2. 实测取证：四项结构性发现

以下全部由脚本读取真实文件得出，非推测。

### 2.1 零个实验达到 D5

长期目标第 5.2 节定义 D5 为「完整学习闭环：在 D4 基础上具备学习路径、复盘题、统计、代表性 E2E 和发布回归证据」。

覆盖矩阵实测深度分布：

| 深度 | 数量 |
|---|---:|
| D2 引导式 | 30 |
| D3 专用模拟 | 22 |
| D4 专用交互 | 26 |
| **D5 完整学习闭环** | **0** |

第 20 节「长期完成判定」要求「学习路径、进度、验证、复盘和统计形成完整闭环」。零个 D5 意味着该条从未被任何单个实验满足过——不是部分满足，是零。

### 2.2 复盘题是 78 个实验共用的四道通用题，且无提示、无选项、无正确答案

实现位于 `apps/web/src/labs/lab-detail.ts:32` 的 `createLabEventRecapQuestions(event)`。每条事件日志固定产出**四道**题：

| 来源 | 题干 |
|---|---|
| 固定 | 这条事件的后端决策是什么，为什么是这个决策？ |
| 固定 | 同样动作切换到另一个变体时，预期信号会如何变化？ |
| 按 `event.phase` 分支 | `attack` → 攻击者控制了哪个输入或动作？／`defense` → 修复版依靠哪个校验或边界阻断？／其他 → 正常业务路径需要保留哪些条件？ |
| 按 `event.decision` 分支 | `accepted` → 系统为什么接受了请求？这是正常接受还是漏洞接受？／`blocked` → 阻断发生在哪个边界？是否影响正常业务？／其他 → 失败原因是输入无效、目标不存在，还是校验不通过？ |

函数入参只有 `event`，**分支依据是 `phase` 与 `decision` 两个通用字段，与实验主题无关**。因此 78 个实验之间不存在任何题目差异：学 `network.ddos` 与学 `social.bec` 看到的四道题完全相同。

关键结构事实是**题目是纯字符串数组**：没有 `hint` 字段，没有选项，没有正确答案，也没有与知识点的绑定。前端只有 `toggleQuestionCompleted` 按 `questionIndex` 记「点过／没点过」（`apps/web/src/labs/event-recap.ts`）。

这决定了 A 组的性质：**不是「改进现有题库质量」，而是从零建立带选项与正确答案的题目模型**。原始规划把该项写成「修掉指向答案的 `hint`」是错的——不存在 `hint` 字段可修，也不存在可判对错的作答语义可改进。

### 2.3 57 个实验（73%）不在任何学习路径中

`apps/web/src/utils/lab-directory.ts` 定义 5 条学习路径，合计引用 **21 个实验**。其余 57 个只能从目录孤立点进，没有前置、没有后续、没有学习顺序。

`LT-034` 交付时的记录是「实现首批静态学习路径」——「首批」是准确的，但四轮过去从未扩展。

### 2.4 引导式第二版模型只服务新建实验，30 个存量场景未迁移，且同构是结构性的

`LT-005`（第一轮）就交付了第二版共享模型，支持多案例、多步骤状态机、证据卡、时间线、分支决策、评分维度。该模型**并未闲置**：`apps/server/src/services/` 下 17 个专用实验服务导入 `createGuidedScenarioMachine`（`bfla`、`clickjacking`、`credential-stuffing`、`formjacking`、`iam-policy-audit`、`insecure-randomness`、`kubernetes-rbac-audit`、`mitb-transaction`、`oauth`、`open-redirect`、`persistence-triage`、`ransomware`、`rate-limit-idempotency`、`rule-alert-triage`、`service-permission-audit`、`session-hijacking`、`workflow-bypass`），且这 17 个全部不在引导式目录内。

问题不是模型没人用，而是**新建实验用第二版、30 个存量引导式场景仍留在第一版**，两套结构长期并存。四轮后实测 `packages/shared/src/guided-scenarios.js`：

| 第二版字段 | 30 个场景中的出现次数 |
|---|---:|
| `steps:` | 0 |
| `cases:` | 0 |
| `evidence:` | 0 |
| `scoringDimensions:` | 0 |

30 个存量场景**一个都没迁移**（`liftV1Scenario` 这个现成的第一版提升函数在 `.d.ts` 中有声明，但全仓无任何调用点，说明迁移通道早已备好却从未启用）。

关键发现是同构的性质。全部 30 个场景由 `scenarioInputs.map(createScenario)` 单一工厂产出，工厂内硬编码：

- `scenarios[]` 恰好 1 个元素
- `controls[]` 恰好 2 个元素（一弱一强）

**因此任何场景都不可能拥有不同的案例数、步骤数或证据类型——同构不是风格选择，是工厂结构决定的。** 第 8 章「一个主题支持多个固定案例」这条在当前架构下无法实现，不是没做，是做不到。

## 3. 三项已确认的方向决策

### 3.1 学习效果验证追踪到知识点级掌握度

不做整体完成率或分数，追踪「每个知识点是否被掌握」。依据：`meta.json` 的 `knowledgePoints` 已在 78 个实验中稳定存在，是天然锚点。

### 3.2 引导式迁移按分类批量推进

不逐个专用化（预算远超本轮），不只挑两类（会长期留下两套并存结构）。按 `network`／`social`／`malware`／`client`／`ai`／`infrastructure`／`supply-chain` 分批，每批一次收口。

### 3.3 本轮不新增安全实验

78 个实验、14 个分类的广度已足够。深度机制未建立前新增只会扩大同一问题的规模。第 9 章 81 条候选继续作为选题池，不进队列。

## 4. B 组的反同构硬约束

第 2.4 节证明同构是结构性的。若迁移只是把第一版数据套进第二版三步模板，等于把同构从 D2 搬到 D3——工作量花了，学习价值没变。

因此 B 组每一项必须满足五条硬性验收条件：

| 约束 | 判定口径 |
|---|---|
| 证据类型主题特有 | `evidence` 卡的 `kind` 与字段必须反映该主题的真实分析对象，不得跨主题复用同一套结构。`network.dns-tunneling` 用查询时间线与熵特征，`social.bec` 用供应商主数据变更与审批链，两者字段定义不应兼容 |
| 步骤数由主题决定 | 禁止全部一律两步或三步。判据是该主题的真实分析流程需要几个决策点。同批次内若步骤数全部相同，须在文档中说明这是主题本身的性质而非模板所致 |
| 控制项数打破「全部 2 个」 | 同批次内应有差异，差异来源是主题复杂度 |
| 禁止单一视图渲染全部场景 | 至少按主题类型分组渲染 |
| 复盘题绑定 A 组知识点 | 不得沿用通用三题 |

`LT-061` 建**同构检测器**：扫描迁移后场景的步骤数、控制项数与证据类型集合，同批次内完全一致时报警。这把「不要千篇一律」从口头约束变成机械判据。

## 5. 五组分工与依赖

| 组 | 编号 | 主题 |
|---|---|---|
| A | `LT-054`～`LT-060` | 学习效果可验证：知识点级掌握度 |
| B | `LT-061`～`LT-072` | 引导式第二版迁移：30 个存量场景并入已在用的第二版模型 |
| C | `LT-073`～`LT-082` | 学习闭环补齐：路径全覆盖、分步提示、测验、笔记 |
| D | `LT-083`～`LT-092` | 深度证据体系：D5 判定与 E6 补齐 |
| E | `LT-093`～`LT-100` | 长期可维护性与第五轮审计 |

依赖关系是刻意的：A 提供知识点绑定口径 → B 迁移时须绑定 → C 补齐闭环组件 → D 才能判 D5 → E 审计。

**D 组的 D5 判定不得先于 A／B／C 完成。** 这条来自第四轮教训：`LT-045` 审计时我记录「78 个验证器都有盲区」，但实测只有 17 个实验存在那类风险，先声明标准再发现无法满足会让标准变成摆设。

## 6. 两条验证纪律

本轮每一项都须遵守，来源是前四轮各栽过一次的具体教训。

**其一：新增门禁必须做注入测试，不接受「全绿」当有效性证据。**
`LT-046` 首版信号检查只扫服务端顶层 `*Signal` 导出，注入 `LT-042` 真实缺陷时**漏判**（实测 `ok true failed 0`），改为从工作台 option 收集后才捕获。

**其二：不得用「机制存在」代替「机制有效」。**
`LT-050` 我用「脚本能跑」误判为「安装可复现」，实际全新克隆装不上依赖、CI 对全新运行已损坏。本轮掌握度判定必须验证「答错时确实判为未掌握」，而非只验证接口返回 200。

## 7. 安全边界（本轮不变）

- 不新增任何攻击能力。所有新增均为学习机制、验证与治理。
- 掌握度数据是本机个人学习数据，不外传、不做云端同步。
- 不引入评分排名或竞争机制——本项目是个人学习工具，不是考试系统。
- 复盘题与选项全部为固定内容，不接受自由输入。
- 防御性解释只说明「为何危险」与「为何修复有效」，不输出可迁移的危险 payload。

### 9.2 规划阶段自查发现并修正的四处事实错误

均在写入队列前修正，避免了把错误前提固化成后续 47 项的验收口径：

1. **「第二版模型搁置四轮」不成立**。17 个专用服务已在使用，模型未闲置；真实问题是两套结构并存。若不改，B 组会被描述成「激活一个没人用的模型」，与实际的「统一两套并存结构」是不同任务。
2. **复盘题实现位置、函数名与题目数量全错**。正确是 `apps/web/src/labs/lab-detail.ts:32` 的 `createLabEventRecapQuestions()`，四道题。
3. **`hint` 指向答案位置整条是虚构的**。题目为纯字符串数组，无 `hint`、无选项、无正确答案，引用的两条提示文案全仓不存在。这处最严重：`LT-054` 与 `LT-060` 原本把硬约束建立在不存在的字段上。修正后 A 组性质由「改进题库质量」变为「从零建立可判对错的题目模型」。
4. **`LT-057` 的「8 个」实测为 7 个**（`bfla` 是 D4，`mitb` 是 D3），已逐一列名。

按第 6 节「其二：不得用『机制存在』代替『机制有效』」的同类逻辑，这四处属于「用『我记得的结构』代替『实测的结构』」。取证脚本本身就是这条纪律的执行。

### 9.3 据实测补入的两条约束

- `lab_recap_question_completions` 唯一键为 `(user_id, trace_id, question_key)`，同一知识点会跨多次运行重复作答，掌握度须跨 trace 聚合并定义「先答错后答对」口径（已写入 `LT-056`）。

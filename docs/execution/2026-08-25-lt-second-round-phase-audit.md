# LT-030 长期目标第二轮阶段审计执行文档

## 1. 目标

在 `LT-027`～`LT-029` 完成后，对长期队列 `LT-001`～`LT-030` 进行第二轮事实审计，确认实验数量、分类、变体、模式、专用/引导式深度、路由入口门禁、Playwright 证据和安全边界与仓库真实状态一致，并基于剩余缺口重排下一轮任务。

## 2. 范围

- 审计 `SECURITY-COVERAGE-LONG-TERM-GOAL.md`、`docs/TODO.md`、覆盖矩阵、元数据和根级脚本。
- 审计 71 个实验、14 个分类和 142 个变体的当前状态。
- 核对 `LT-027` 专用化计数、`LT-028` 入口一致性门禁和 `LT-029` 页面级证据。
- 记录根级 `pnpm verify`、目标 Playwright 和静态差异检查结果。
- 新增第二轮审计后的后续任务队列，按结构性风险、学习价值和工程依赖排序。

不新增实验运行时代码，不扩展安全攻击能力，不修改数据库 schema。

## 3. 操作步骤

1. 汇总覆盖验证器、入口验证器和元数据的真实统计。
2. 核对长期目标、README、AGENTS、TODO 和覆盖矩阵的当前基线描述。
3. 审阅 `LT-001`～`LT-030` 的完成证据，缺少证据的任务不得标记完成。
4. 运行根级门禁和 `LT-029` 目标 Playwright，记录准确结果。
5. 盘点仍未覆盖的平台、学习体验、安全主题和工程治理缺口。
6. 按依赖顺序建立 `LT-031` 起的下一轮任务队列。
7. 回填第二轮审计结论，并统一所有当前进度文档。

## 4. 实施建议

- 使用验证器输出和真实元数据作为数量事实，不手工推算。
- 历史执行文档保留当时基线，不批量改写历史数字；只同步当前权威文档。
- 后续队列优先补工程一致性和高价值学习闭环，再增加新主题数量。
- 每个后续任务仍需独立执行文档，不在本轮直接实现。

## 5. 潜在风险分析

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 文档与实现计数漂移 | 无法判断真实进度 | 以验证器和元数据实算结果回填 |
| 把代码存在误判为任务完成 | 未验证实现进入完成队列 | 每项要求命令证据和完成记录 |
| 改写历史执行事实 | 失去可追溯性 | 仅更新当前总纲、TODO、README、AGENTS 和矩阵 |
| 后续队列范围失控 | 偏离个人学习平台定位 | 按结构缺口、依赖和安全边界限制任务数量 |
| 审计只做文档检查 | 无法证明当前行为 | 同时运行根级门禁和代表性页面验证 |

## 6. 优化方案

- 将 Web 入口一致性验证纳入根级 `verify`，以后由机器持续维护 142 个变体的入口事实。
- 下一轮继续补 API 入口反向检查和新增分类的页面证据，减少人工审计成本。
- 把平台功能、实验内容、页面证据和发布能力继续分开统计，避免单一完成百分比掩盖缺口。

2. Web 入口已有反向门禁，API entrypoints、脚本路径和文档路径仍缺统一机器校验。
3. 学习路径、目录多维筛选、全文/知识点搜索仍停留在 `LT-019` 规划阶段。
4. token 生命周期、会话吊销和本机账号维护仍未形成完整平台治理闭环。
5. API 属性级授权、业务幂等/竞态、秘密生命周期、Windows 事件日志、Kubernetes/IaC 仍是结构性内容缺口。

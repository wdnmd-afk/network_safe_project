## 1. 目标

建立测试覆盖率基线（先观察，不设门禁阈值），以及失败证据、日志位置和排障说明。

## 2. 实施前确认的现状

| 项目 | 实测结论 |
|---|---|
| 覆盖率配置 | `vite.config.ts` 与 `package.json` 均无 coverage 配置 |
| 覆盖率工具 | **未安装任何 provider** |
| Node 内置能力 | Node 22 支持 `--experimental-test-coverage`，可测服务端且无需新依赖 |
| vitest 覆盖率 | 必须配套 `@vitest/coverage-v8`，缺失时报 `MISSING DEPENDENCY` |

## 3. 关于新增依赖的判断

项目规则是「非必要不引入新依赖」（`AGENTS.md` 第 11 节）。本切片新增了一个：`@vitest/coverage-v8@2.1.9`。

判断依据：

- 服务端用 Node 内置能力即可，**不新增依赖**。
- 前端的 vitest 没有内置覆盖率，`@vitest/coverage-v8` 是其官方配套 provider，无替代方案。
- 若只测服务端，会得到半个基线——394 个服务端测试有数据、285 个前端测试没有，这样的「基线」无法支撑后续阈值决策。
- 该包仅开发期使用（`devDependencies`），版本与已装 vitest 2.1.9 精确对齐，不引入运行时体积。

因此判定为「必要」。这是本轮 `LT-046`～`LT-052` 七个切片中唯一新增的依赖。

## 4. 交付内容

### 4.1 覆盖率命令

| 命令 | 范围 | 工具 |
|---|---|---|
| `pnpm coverage:server` | 服务端 394 个测试 | Node 内置 |
| `pnpm coverage:web` | 前端 285 个测试 | `@vitest/coverage-v8` |
| `pnpm coverage` | 两者依次执行 | — |

**不纳入 `pnpm verify`**：覆盖率测量明显慢于普通测试，且当前无阈值可判定通过与否，放进门禁只会拖慢每次验证而不产生任何判据。这与前六个切片的做法不同——那些检查都有明确的通过／失败判据，因此纳入门禁是有意义的。

### 4.2 `docs/testing/coverage-baseline.md`

记录测量方式、观测基线、前端数字偏低的真实原因、设定阈值前需先回答的四个问题，以及失败证据位置与排障顺序。

## 5. 观测基线（首次测量）

| 范围 | 测试数 | 行 | 分支 | 函数 |
|---|---:|---:|---:|---:|
| 服务端 | 394/394 | 72.65% | 81.11% | 70.52% |
| 前端 | 285/285 | 31.01% | 79.11% | 58.94% |

### 5.1 前端 31.01% 不等于「前端测试很差」

这个数字容易被误读，实际原因是测试类型与覆盖统计范围不匹配：

- 285 个前端测试针对 `src/labs/*.ts`（固定契约与格式化函数）与 `src/api/*.ts`（请求构造与响应处理）。
- `src/views/*.vue` 约 50 个组件文件**全部为 0%**，没有任何组件渲染测试。这些文件动辄数百行，大幅稀释整体行覆盖率。
- 组件行为实际由 Playwright E2E 覆盖（31 个实验具备 E6 三向页面验证），但 E2E 不参与 vitest 覆盖率统计。

因此分支 79.11% 与函数 58.94% 比行覆盖率更能反映被测代码质量。文档中已写明这一点，避免后续有人据 31% 得出错误结论。

## 6. 为何不设阈值

长期目标第 10.2 节原文即为「先观察再决定门禁阈值」。在只有一次测量的情况下设阈值属凭空取数：过低无约束力，过高会立刻阻塞正常开发。

文档中列出了设阈值前需先回答的四个问题，其中最关键的是：统计范围是否应排除 `src/views/*.vue`。在补齐组件测试前，包含它们意味着阈值实质由「视图代码总行数」决定而非测试质量——这会让阈值在新增实验页面时自动变得更难达成，与测试质量无关。

## 7. 实施过程中触发并修复的一个副作用

新增 `@vitest/coverage-v8` 触发依赖重装后，服务端测试出现大面积失败：394 个测试变为 61 个、53 个失败，报 `@prisma/client did not initialize yet`。

排查过程有一次误判值得记录：初见失败时我以为是自己新加的 `--experimental-test-coverage` 标志所致，于是改动脚本写法。但对照实验显示**不带覆盖率标志的 `pnpm test` 也同样失败**，说明与覆盖率无关。

真实原因：`pnpm add` 重装依赖改变了 Prisma 客户端的生成路径哈希（从 `...1d040ab...` 变为 `...d64af47...`），已生成的客户端相对新位置失效。

处置：`pnpm --filter @network-safe/server prisma:generate`，随后 394/394 恢复。

该模式已写入排障文档的「已知环境类失败模式」表——它的特征是**大面积失败而非个别失败**，这正是区分环境问题与代码问题的判据。

## 8. 验证

- `pnpm coverage:server`：394/394 通过，行 72.65%／分支 81.11%／函数 70.52%。
- `pnpm coverage:web`：285/285 通过，行 31.01%／分支 79.11%／函数 58.94%。
- 依赖新增后 `pnpm verify` EXIT=0。
- `git diff --check` 通过。

脚本写法上有一处需注意：`coverage:server` 委托给服务端自身的 `test:coverage`，glob 不加引号交由 node 展开。这与既有 `test` 脚本一致；加引号经 `pnpm exec` 传递时会导致 glob 展开异常。

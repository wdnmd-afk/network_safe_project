## 1. 背景与目标

第三轮审计后续队列 `LT-041`～`LT-044` 已全部收口，并在收口后补齐了三个新实验的 E6 页面证据。按 `LT-020`、`LT-030`、`LT-040` 建立的惯例，队列清空后需要执行一次阶段审计：核对事实基线、复核既有门禁的有效性、重排下一轮队列。

本审计只读取仓库内文件与运行本机验证命令，不访问外部目标，不读取真实凭据。

## 4. 审计结果：门禁有效性缺陷

本轮最重要的发现不是计数偏差，而是验证体系的结构性盲区。

### 4.1 专项验证器普遍使用存在性检查

抽样核对 `iam-policy-audit`、`rate-limit-idempotency`、`persistence-triage`、`mitb` 四个验证器，模式完全一致，并可推及全部 78 个：

- 均把服务端服务、`app.ts`、前端 API client、前端 labs 模块、路由、视图读入并拼接为 `combinedImplementation`。
- 随后断言"某固定 key 片段在 `combinedImplementation` 中出现"。
- 无一个验证器比对"前端 `recommendedPath` 的元素是否等于服务端注册的 optionKey"。

后果：当前端写错 key、服务端写对时，拼接串里仍然包含正确值，断言通过。`LT-042` 的四处 key 错误（scenarioKey 加三个 optionKey）就是这样穿过 18/18 专项检查、`pnpm verify` 和入口一致性门禁的。缺陷最终由 Playwright 页面用例暴露，而当时该实验尚无 E6 证据。

影响面：48 个专用实验全部依赖这一模式，任何一个都可能存在同类未被发现的不一致。

### 4.2 E6 覆盖率不足使前述盲区无法被兜住

47 个实验（占 60%）没有 E6 页面证据。由于专项验证器无法检出前后端不一致，E6 实际上是这类缺陷的唯一可靠防线。当前 60% 的实验缺少这道防线。

### 4.3 覆盖矩阵统计表与正文脱钩

`docs/design/security-coverage-matrix.md` 第 2 节的总体统计表在 `LT-042`～`LT-044` 三个切片中一直未更新，长期停留在 75 实验 / 45 专用 / E6 28 的旧基线，直到本轮审计前才修正。原因是 `verify-security-coverage.mjs` 只比对"矩阵行"与元数据，不校验这张统计表，因此三轮都没有报错。

### 4.4 文档批量改写缺乏并发保护

`LT-044` 收口时出现过同一文档内"44/44 已完成"与"`LT-044` 未完成"并存的矛盾，原因是先后两个改写脚本，后者基于陈旧副本回写，覆盖了前者已写入的勾选。该矛盾进入了提交，由随后的独立提交修正。

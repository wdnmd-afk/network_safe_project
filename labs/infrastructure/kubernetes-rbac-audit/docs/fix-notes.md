# RBAC 范围收敛修复思路

## 根因

`virtual-cluster-admin-broad-binding` 的问题不是单一字段，而是四要素同时放宽：集群级角色范围、通配符动词、通配符资源、宽泛主体组，并额外允许 `escalate` / `bind` 类提权动词。任何一项单独收紧都不足以消除提权可达性。

## 修复策略

固定加固基线 `virtual-namespaced-readonly-binding` 登记五项收敛控制，缺一不可：

1. **角色范围降级为命名空间**（`namespace-scoped`）：把授权面限制在单个命名空间内，而不是整个集群。
2. **动词收敛为只读**（`read-only-verbs`）：只允许 get / list / watch 类动词，避免写入与删除。
3. **资源显式列出**（`explicit-resources`）：不使用资源通配符，避免未来新增资源类型被自动纳入授权。
4. **主体收敛为具名 ServiceAccount**（`named-service-account`）：绑定到确定的工作负载身份，而不是宽泛用户组。
5. **禁止提权动词**（`escalationVerbsAllowed` 为假）：显式排除 `escalate` / `bind`，阻断自行扩权路径。

五项同时成立后，该绑定的固定发现数为 0、关键组合风险为 0、最小权限控制数为 5，提权不可达。

## 为什么修复有效

- 前三项收敛授权的"范围"，第四项收敛授权的"对象"，第五项收敛授权的"可变性"。
- 三类关键组合风险各自需要两个以上条件同时成立，收敛任一维度即可打断组合，但只有五项齐备才能让关键风险计数归零。
- 收敛后正常业务仍可继续：`verify-namespaced-baseline` 路径证明只读工作负载在最小权限下仍能通过复核，修复不是以牺牲可用性换取安全。

## 复盘要点

- 审查 RoleBinding 时要同时看角色范围、动词、资源、主体和提权动词五个维度，不能只看角色名是否叫 admin。
- 集群级绑定应作为例外而非默认，且必须有明确的审批与到期机制。
- 提权动词（`escalate`、`bind`、`impersonate`）应单独列入审计清单。

## 边界说明

- 本文档只解释固定虚构快照上的收敛逻辑，不提供可直接应用于真实集群的清单。
- 修复版只做固定摘要复核，不调用 Kubernetes API、`kubectl`、Helm 或任何云 SDK。
- 未知输入统一脱敏阻断，不回显原始值。
